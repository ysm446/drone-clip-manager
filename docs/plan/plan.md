# plan — drone-clip-manager 実装方針と予定

作成日時: 2026-07-08 12:29
更新日時: 2026-08-14 20:18

実装方針・優先順位・今後の予定をまとめる。詳細仕様は [../spec.md](../spec.md)、目的は [goals.md](goals.md) を参照。

## アーキテクチャ方針

```
Renderer (React)        Library / Editor / Export Queue、<video> プレビュー
      │ IPC (invoke/handle)
Main Process (Node)     MediaService / ThumbService / ExportService / DB(better-sqlite3)
      │ child_process
ffmpeg / ffprobe
```

- **バックエンドサイドカーは持たない**。Electron メインプロセスから直接 `ffmpeg` / `ffprobe` を叩く。
- 将来のカメラモーション解析（Phase 3）は、メインプロセス下に `AnalysisService`（Python サイドカー）を差し込む形にする。
  今回は接続点（DB の `motion_tags` 受け皿、サービス分離）だけ用意し、実装しない。

## ストレージ / メタデータ配置

- ルートフォルダは **ユーザーがダイアログで指定**（ハードコードしない）。設定に永続化し次回復元。複数ルート切替可。
- メタデータは **ルート直下の `.dcm/`** に作成する:
  - `library.db`（SQLite: `videos` / `keyframes` / `segments`）
  - `thumbnails/`（サムネイルキャッシュ）
  - `proxies/`（将来のプレビュープロキシ）
- `videos.path` / `thumb_path` は **ルート相対パス** で保持し、フォルダ移動に耐える。

## 技術的な肝: キーフレームとロスレス切り出し

- キーフレーム抽出は ffprobe のパケットフラグから高速取得し、取り込み時に `keyframes` へキャッシュ。
- スナップ: **in は直前キーフレーム / out は直後キーフレーム**（区間が縮まないよう外側へ丸める）。UI にマーカー表示。
- 書き出し: `ffmpeg -ss <in_snapped> -i input -t <duration> -c copy -map 0 -avoid_negative_ts make_zero out.mp4`
  - `-ss` は `-i` の前（input seeking）。区間長は `-to` ではなく `-t`。音声も copy。
- ExportService は `mode: "keyframe" | "smart"` を切替可能なIFにしておく。今回は `keyframe` のみ実装。

## 開発フェーズと優先順位

### Phase 1 — ライブラリ基盤
- ルートフォルダ指定・永続化、`.dcm/` 初期化、DB スキーマ作成
- ルート配下の再帰走査で動画検出、ffprobe メタ抽出、DB 登録
- サムネイル生成（生成タイミングは §オープン論点）
- Library View（グリッド/リスト、バッジ、フィルタ、検索）
- プレビュー再生（`<video>`）

### Phase 2 — 区間 & 書き出し（← MVP ゴール）
- キーフレーム抽出・タイムライン可視化
- 区間ブックマーク CRUD（複数・ラベル・メモ・色）
- in/out スナップ（前/後キーフレーム）
- ロスレス書き出し（stream copy、単発 / バッチ）
- Export Queue（出力先、命名テンプレート、進捗、成功/失敗ログ）

### Phase 2.5 — クリップ一覧ビュー（区間を独立したクリップとして扱う）✅ 完了（2026-07-08）

区間（segment）を「動画に紐づくブックマーク」から一歩進めて、**独立したクリップとして横断一覧**する
ビューを追加する。名前どおりの "clip manager" にする中核機能。

- **狙い**: 全動画をまたいで「使えるカット」を俯瞰・整理・書き出しできるようにする。Export の
  「複数動画横断キュー」（spec §7.3）もこのビューから素直に実現する。
- **表示切替**: ライブラリ（動画一覧）⟷ クリップ（区間一覧）をトグル/タブで切替。
- **クリップカード**（グリッド or リスト）: in 点サムネイル / 元動画名 / ラベル / `in–out`・長さ /
  コーデック・解像度バッジ。
- **アクション**: クリック → 元動画を開いて in へシーク（範囲ループ再生も検討）／ラベル編集 ／
  書き出し ／ 削除。
- **複数選択 → まとめて書き出し**（動画横断）。既存の Export モーダルをクリップ選択ベースに拡張。
- **絞り込み/ソート**: 元動画・日付・ラベル（将来: モーションタグ）。
- **実装メモ**:
  - データは `segments` にあるので、全区間を集める IPC（例 `segments:listAll` 結合クエリ）を追加。
  - クリップサムネイル: in 点のフレームを ffmpeg で 1 枚生成して `.dcm/thumbnails/` にキャッシュ。
  - 既存の区間リスト（Editor 内）とロジックを共有できる形にする。

### Phase 2.6 — クリップのシーケンス（つないで連続再生 → 連結書き出し）★次の主要機能
クリップを並べて/つないで、**1 本のシーケンス（ラフカット）として連続再生**し、そのまま
**再エンコードなしで連結書き出し**する。

- **段階**:
  1. **線形シーケンス（まず本命）**: クリップを順に並べる（ドラッグ並べ替え）→ 連続再生 → concat 書き出し。
  2. **ノードグラフ**: クリップをノードとして線でつなぎ、順路を組んで再生。分岐は発展として後回し。
- **進捗（2026-07-09）**: ユーザー要望により **2. ノードグラフから着手し、一本道・再生までを実装済み**
  （「シーケンス」タブ）。次は順路の **無劣化連結書き出し（concat）**。分岐と線形専用 UI は後続。
- **再生**: mpv のプレイリスト（`loadfile ... append` + 各クリップの in/out）で順再生。クリップ境界の
  ギャップレス度は要検証。
- **連結書き出し**: 同一コーデック/パラメータ（DJI 素材）なら **ffmpeg concat demuxer で stream copy 連結**
  （無劣化）。パラメータ差があるものは対象外 or 将来 smart 連結。spec §9「跨ぎ書き出し」がここに繋がる。
  → **実装済み（2026-07-12）**。2 段階 stream copy（切り出し → concat）+ 進捗モーダル。
- **論点**: 境界の滑らかさ、分岐ノードの再生ルート選択 UX（線形なら不要）。

#### Phase 2.6b — 連結書き出しに BGM を載せる ✅ 完了（2026-08-14 / Phase 2.6c 段階 4 と同時に実装）

連結書き出しのオプションとして BGM を 1 曲指定し、フェード付きで音声に載せる。
「映像はロスレスのまま」という設計思想は崩さない（copy 維持、音声のみエンコード）。

- **仕様**:
  - BGM フォルダ（既存の BGM プレイヤーと同じ `getBgm()` の曲一覧）から 1 曲選択。「なし」も可（従来どおり）。
  - 音声は **BGM で上書き**（元音声は出力に含めない。ドローン素材は元音声が無い/不要なため）。
  - **フェードイン / フェードアウト秒数**を設定可能（0 で無効）。
  - 映像は stream copy（無劣化）のまま。音声のみ AAC（256k 目安）にエンコード。
  - 曲がシーケンスより**長い場合は末尾で切る**。**短い場合は無音のまま**終わる（ループはしない）。
- **実装方針**:
  - `exportConcat` に `bgm?: { relPath, fadeInSec, fadeOutSec }` を追加。concat 結果を一時ファイルに出し、
    3 段目で BGM を合成して最終出力（進捗は cut / concat / bgm の 3 段階、総秒数×3 が分母）。
  - ffmpeg: `-i concat.mp4 -i music -map 0:v -map 1:a -c:v copy -c:a aac -b:a 256k
    -af "apad=whole_dur=T[,afade=t=in:st=0:d=fi][,afade=t=out:st=T-fo:d=fo]" -t T`
    （`apad` で曲が短い場合に無音を延長し、`-t` で総尺 T に切る。BGM パスは `resolveInBgm()` で解決）。
  - UI: 「連結書き出し…」押下 → 設定モーダル（BGM 選択 / フェードイン / フェードアウト）→
    出力先を選んで開始。既存の進捗 / 結果モーダルに続く。
  - 型: `ConcatBgm` を追加、`exportSequenceConcat(items, outDir, name, bgm?)`、
    `ConcatProgress.phase` に `'bgm'` を追加。
- **論点**: フェードの既定値（案: イン 1s / アウト 2s）、曲の開始オフセット指定（サビ合わせ）は将来。

#### Phase 2.6c — 音楽同期タイムライン（ビート検出 + クリップの拍スナップ）★構想確定（2026-08-14）

BGM の拍 / 小節を検出し、**曲を主・クリップを従**として並べる線形タイムラインビューを追加する。
クリップの尺を「秒」ではなく「拍 / 小節」で持つことで、**曲を差し替えると全クリップが自動で並び直る**。

- **基本方針（2026-08-14 決定）**:
  - **音楽が主、クリップが従**。クリップの尺は曲の拍・小節に従属する。
  - **前詰め固定**（クリップ間のギャップを持たない）。全尺がビート単位なら、前詰めするだけで
    全カットがビート上に乗る。開始位置を保持する必要もない。
  - **縮める方向のみ自動**。伸ばす（元 segment の範囲外へ出る）のは人間の明示操作にする。
  - **曲の差し替えで全体長は合わせない**。足りない / 余るはそのまま見せ、あとは人間が調整する。
  - **元の segment は不変**。ライブラリ側のブックマーク（6.5 秒等）を音楽都合で書き換えない。

- **データモデル**:
  - シーケンスの実体は既存を共有（新エンティティを作らない）。`sequences` / `sequence_nodes` /
    `sequence_edges` を**別ビューとして見る**だけ。順序は既存のエッジチェーンで表現する。
  - `sequence_nodes` に列追加:
    - `units`（尺の意図。例 8 = 8 拍）/ `unit_kind`（`'beat' | 'bar'`）
    - `src_offset`（segment 内のどこから使うか。既定 0 = 先頭。縮めたときの逃げ場）
    - `auto_shrunk`（曲差し替えで自動的に単位を下げた印。UI 表示用）
  - 新テーブル `sequence_bgm(sequence_id, rel_path, bpm, offset_sec, beats_per_bar, start_offset_sec)`
    — 曲の指定と**手動補正値**のみを持つ。検出結果そのものは曲側のキャッシュに置く。
  - **グリッドの正本は「ビート時刻の配列」**（BPM + オフセットではない）。実素材の検証（2026-08-14）で、
    AI 生成 BGM の一部は**曲自体のテンポが 1〜2 BPM ゆっくり流れる**ことが分かった（下記「検証結果」）。
    単一 BPM では表せないため、キャッシュには拍ごとの時刻配列を持ち、`bpm` は表示・手動補正用の
    要約値として扱う。前詰め・小節単位という設計はビート配列でもそのまま成立する。
  - **実尺は保存しない**。`尺 = units × (60 / bpm) [× beats_per_bar]` で毎回算出する。
    秒で保存すると曲を差し替えたときに元の意図（何小節か）を復元できず、差し替えのたびにズレが溜まる。
  - 拍子は `beats_per_bar` を持つが、**UI は 4/4 固定**で始める。

- **ビートグリッドの抽象（複数曲への拡張余地）**:
  - v1 は **1 シーケンス 1 曲**。ただし将来「複数曲を並べる」ため、グリッドは BPM 単体の数値ではなく
    **`timeToBeat()` / `beatToTime()` を持つグリッドオブジェクト**として実装する。内部を
    「曲の配列（各曲: 開始時刻・BPM・オフセット）」に差し替えれば、曲の切り替わりでテンポと
    小節番号がリセットされる形にそのまま拡張できる。
  - 前詰めなので各クリップの開始時刻は先頭から順に確定する。複数曲でも
    「開始時刻 → その時刻を含む曲の BPM → 尺」の順で一意に決まり、計算が循環しない。

- **リズム検出**:
  - `ffmpeg -i track -ac 1 -ar 11025 -f f32le -` で PCM を取得 → メインプロセスで純 TS 解析。
    **依存追加なし・サイドカーなし**の方針を維持する。ffmpeg 自体にビート検出は無くデコーダとして使う。
    1. spectral flux のオンセット包絡（窓 1024 / ホップ 128 = 86fps、対数圧縮 + 局所平均の除去）
    2. 自己相関で BPM 候補 → コムフィルタで大域 BPM を精密化（多段。下記参照）
    3. **動的計画法によるビート追従**（Ellis 方式。大域 BPM を目標周期に、拍ごとの間隔逸脱を
       `-α(log(Δ/τ))²` で罰する。α=300 が既定）→ **拍の時刻配列**を得る
    4. 4 拍周期でオンセット強度が最大の位相を小節頭にする
  - **固定グリッドと DP 追従の使い分け**: 固定 BPM のグリッドでも十分に合う曲（平均ズレ 20ms 以下）は
    **固定グリッドを採用する**。DP は拍を実音に吸着させるため、テンポが完全に一定の曲でも拍間隔が
    わずかに揺れ（例 `Bloom Drift 2` は瞬間 BPM 123〜132）、小節の秒数が一定でなくなる。
    音楽的に素直な「小節 = 常に同じ尺」を保てるところは保つ。
  - **essentia.js は不要と判断**（2026-08-14 検証）。外れていた曲の原因はオンセット検出の質ではなく
    「単一 BPM を強制していたこと」で、DP 追従（約 80 行 / 1 曲あたり 1ms）で解消した。
    essentia.js の `RhythmExtractor2013` も本質的に同じことをしており、4MB 級の WASM を抱える
    見返りが無い。加えて essentia.js には使える小節頭推定が無く、そこは自前ロジックのまま。
    実運用でオンセット包絡では説明できない失敗が出たら再検討する。
  - 自動検出は初期値と割り切り、**手動補正 UI を必ず用意**する（BPM 数値 / オフセット微調整 /
    タップテンポ / 半・倍テンポ切替）。典型的な失敗は倍・半テンポと小節頭の 1 拍ズレ。
  - 波形ピークと検出結果は `.dcm/` 配下に曲単位でキャッシュ（鍵: パス + サイズ + mtime）。
    同じ曲を複数シーケンスで使っても解析は 1 回で済む。
  - **BPM は曲全体で精密化する必要がある**。3 分の曲では 0.1 BPM の誤差が末尾で 0.14 秒
    （128BPM で約 1/3 拍）のズレになる。粗い刻みの探索ではコムフィルタの鋭いピーク（幅 0.02〜0.03 BPM）を
    飛び越すため、**窓を 30 秒 → 60 秒 →…→ 全体と伸ばしながら刻みを細かくする多段精密化**を使う。
  - **検証結果（2026-08-14 / 手持ちの BGM 54 曲）**: プロトタイプを実素材で計測した。
    - 合成クリック（既知 BPM）で誤差 0.005 BPM 以内。解析時間は 3 分の WAV で **0.4〜1.6 秒**
      （8 分の曲でも 1.6 秒）。DP 追従の追加コストは 1 曲あたり 1ms。依存追加なし。
    - ビートと実オンセットの**平均ズレ**（54 曲）:

      | 区分 | 固定 BPM のみ | DP 追従あり |
      |---|---|---|
      | 15ms 以下 | 9 曲 | **51 曲** |
      | 30ms 以下 | 14 曲 | 3 曲 |
      | 60ms 以下 | 28 曲 | 0 曲 |
      | 60ms 超 | 3 曲 | **0 曲** |
      | 平均 / 最悪 | 32.2ms / 75ms | **7.0ms / 24ms** |

    - **テンポが一定でない曲が実在する**（外れの原因はすべてこれだった）: `Moss and Moon`
      117.97 → 113.88、`Against Her Chest 2` 120.13 → 117.06、`Velvet Night` 89.21 → 86.93、
      `Living Canopy` 150.0 → 148.8。30 秒窓ごとに BPM を測ると単調に下がる。
      一方 `Bloom Drift 2` / `Mountains and Clouds` は全編で幅 0.07 BPM 以内。**曲によって二極化する**。
      AI 生成 BGM は DAW のグリッドから作られないため、これは想定内として扱う。
    - → 上記「グリッドの正本はビート配列」の根拠。
    - 環境音・合唱系（`Forest Choir`: 8 分でテンポが 68 → 75.8 まで動く）は明確な拍が無く、
      DP でも安定しない。**この種の曲は拍スナップに向かないと UI で警告**する。
    - 実装上の落とし穴 2 つ（プロトタイプで踏んだ）: ①コムスコアは拍数で正規化すると半テンポと
      同値になるため、最終選択にテンポ事前分布を掛けないと倍・半を誤る。②候補の順位付けを冒頭で
      行うと、イントロに打楽器が無い曲で倍率を誤る（中盤で行う）。

- **UI（新ビュー: 音楽タイムライン）**:
  - トラックは **映像 1 列 + 曲 1 本**のみ。オーバーラップ / トランジション / 複数映像トラックは
    stream copy と原理的に両立しないため持たない。
  - **トラックの並びは「曲が上・クリップが下」**（2026-08-14 決定）。この機能は「曲に映像を合わせる」
    ものなので、基準になる曲を上に置いて視線の流れと一致させる。NLE の慣習（映像が上）には
    合わせない。既存のノードグラフとは別ビューなので揃える必要が薄いため。
  - 横軸は時間ベースで描画、ズームは小節単位にスナップ。波形 + 小節線（濃）/ 拍線（淡）。
    小節番号はズームに応じて 1 / 4 / 8 小節ごとに間引く。
  - **タイムライン上でのブロックパズル的な操作**（2026-08-14 要望）: クリップパレットからの DnD 配置、
    タイムライン上でのドラッグ並べ替え（挿入位置インジケータ → ドロップで前詰め再計算）。
    → 未着手項目「線形シーケンス（ドラッグ並べ替え UI）」は、これで解消される。
  - 尺の変更: クリップ端のドラッグで単位に吸着。単位候補は
    `1拍 / 2拍 / 1小節 / 2小節 / 3小節 / 4小節 / 6小節 / 8小節`（**最小 1 拍**。128BPM で 0.47 秒）。
    **非 2 冪（3 / 6 小節）を含める**（2026-08-14 決定）。素材の尺を活かせる刻みが増えるため
    （6.5 秒のクリップは 2 小節 = 3.75 秒まで落ちるが、3 小節なら 5.625 秒で収まる）。
    自動縮小で 1 段下げるときも、この並びの 1 つ下を採る。
  - 使用範囲のスライド（`src_offset`）: Alt + 中身ドラッグ（Resolve のスリップ編集に相当）。
    ドローン映像は「見どころが後半」が多く、頭から一律に切ると台無しになるため必須。
  - 曲より短い / 長いが一目で分かること: 曲のグリッドは**クリップが尽きた先も描き続け**（余った小節が
    見える）、曲の終端を越えた部分はグレー表示。ヘッダに「曲より N 秒短い / M 小節分空き」を常時表示。
  - Undo は既存の `undo.ts` に相乗りする。
  - UI は [../design/style-guide.md](../design/style-guide.md) に従う。BGM 系（`.bgm-*`）と
    タイムライン系（`.tl-*`）のスタイルは共通化しない既存方針を維持する。

- **プレビュー再生**:
  - シーケンス再生は Renderer の `<video>`（`App.tsx` の `seqPlayback`）で行っているため、
    BGM の `<audio>` と同一プロセスで同期できる（mpv 経路ではない）。
  - **`<audio>` をマスタークロックにし、映像を追従させる**。クリップ境界の seek で映像が一瞬遅れても
    **音は絶対に止めない**（音が途切れると拍の判断ができなくなるため）。
  - 小節範囲を指定したループ再生を用意する。

- **曲を差し替えたときの挙動**:
  - BPM が変われば全クリップの実尺が再計算され、合計長も変わる。**全体長を曲に合わせる調整はしない。**
  - `units` が元 segment に収まらなくなった場合は、**収まる最大の単位へ自動で 1 段下げる**
    （例 4 小節 → 2 小節）。尺をそのまま残すと**以降のカットが全部ビートからズレる**（連結なので後ろへ
    波及する）ため。下げたクリップには `auto_shrunk` を立て、差し替え直後に確認できるようにする。
  - `src_offset` は保持する（「クリップのどこを使うか」という判断は差し替えを跨いで生き残る）。

- **書き出し**:
  - Phase 2.6b の BGM 合成経路に乗せる。映像は stream copy のまま、音声のみ AAC。
  - **in はキーフレームスナップのまま、out を `in + 算出尺` にする**。連結後のカット点は各クリップ尺の
    累積で決まるため、これで**カットは正確にビート上に乗り、ロスレスと両立する**。
    ※ 末尾を GOP 途中で切ったときの数フレームの扱いは実機検証が必要。
  - ビート秒は動画 fps のフレーム番号に量子化して持つ（29.97 等で累積誤差が出るため）。
  - `sequence_bgm.start_offset_sec`（イントロ飛ばし / サビ合わせ）を書き出しにも反映する。

- **段階**:
  1. **検出のみ** ✅ 完了（2026-08-14）: BPM / 小節頭の検出 + BGM プレイヤーにビート表示とタップテンポ。
     `src/main/services/beats.ts` + IPC `bgm:analyzeBeats`。実装は progress.md を参照。
  2. **タイムライン表示** ✅ 完了（2026-08-14）: 波形 + 小節グリッド + 前詰めのクリップ列（読み取り専用）。
  3. **編集** ✅ 完了（2026-08-14）: 3a = 尺の単位変更・`src_offset` スライド・曲差し替えと自動縮小・
     `units` の永続化。3b = タイムライン上での DnD 配置と並べ替え。
  4. **書き出し** ✅ 完了（2026-08-14）: 2.6b（BGM 合成）をここで実装し、音楽ビュー専用の
     書き出しを追加。in はキーフレームへ丸め、尺はフレーム単位へ量子化して誤差を次のクリップへ
     持ち越す（累積ズレを半フレーム未満に抑える）。実素材でカットのズレ最大 7.7ms を確認。

- **論点（未決）**:
  - テンポ揺れの大きい曲（例 `Living Canopy`）をどう扱うか。案: ①ビート配列をそのまま使う（拍は曲に
    正確に乗るが、小節の秒数が場所により変わる）／②警告のみ出して固定 BPM で通す。①が素直だが、
    「4 小節 = 常に同じ尺」という前提が崩れる点をユーザーがどう感じるかは要確認。
  - `auto_shrunk` クリップの一覧 / 順送りジャンプを用意するか（差し替え直後の確認導線）。
  - 曲の差し替え時に `start_offset_sec` をリセットするか保持するか（曲が変われば意味が変わるため
    リセット想定）。
  - 複数曲へ拡張したとき、曲の境界をクリップが跨ぐ場合の扱い。
  - ノードグラフ側で分岐を作ったシーケンスは、タイムラインには最長チェーンしか映らない（この非対称は許容）。

### Phase 2.7 — キーフレームフラグと区間スナップ（マーキング補助）★予定
動画を見ながら**ショートカットでキーフレームにフラグ（マーカー）を立て**、そのフラグを基準に区間を張る
ワークフロー。区間の端（タイムラインの区間バー＝「テープ」）はフラグへ磁石スナップする。

- **フラグ設置**: 再生位置でショートカット（例 `F` / `M`）を押すと、その位置を**最寄り（または直前）の
  キーフレームにスナップしてフラグを立てる**。もう一度押す/別キーで解除。フラグはキーフレーム上にあるため、
  区間がフラグに揃えば**ロスレス書き出しの整合が保たれる**（フラグ = ユーザーが選んだキーフレームの部分集合）。
- **表示**: タイムラインにフラグ専用マーカー（キーフレーム tick とは別色/形）で表示。ホバーで時刻。
- **区間を張る**:
  - フラグを基準に区間を作る（例: 直近 2 フラグ、または「前フラグ → 次フラグ」）。
  - 区間バーの端ドラッグ / 移動時に、近傍フラグへ**磁石スナップ**（フラグが無い箇所は従来のキーフレーム
    スナップ in=前 / out=後）。
- **永続化**: フラグを動画単位で保存（新テーブル `flags(video_rel_path, pts_time)` など）。
- **論点**:
  - フラグのスナップは「最寄りキーフレーム」か「直前キーフレーム」か。
  - 区間生成のキー操作（フラグ 2 点指定 / in・out を個別にフラグへ）と既存 `I` / `O` の役割分担。
  - スナップの磁石半径（px / 秒）、スナップ一時無効の修飾キー（Alt でフリー移動など）。

### Phase 2.8 — ユーザーラベル / タグ（分類・絞り込み）★予定
動画・クリップに**ユーザー定義のラベル（タグ）**を付けて分類・検索・絞り込みできるようにする。
地名・時間帯（朝 / 昼 / 夕方 / 夜）・被写体・天候などを、後から自由に付与する。

- **対象**: 動画（フライト単位）と クリップ（区間）。両方に付けられるのが理想（要判断: まず区間から）。
- **タグの形**: 自由記述タグ + 任意で「カテゴリ（名前空間）」。例 `地名:ツェルマット` / `時間帯:夕方`。
  カテゴリ無しの素のタグも可。既存の `segment.label`（1 つの見出し）とは別に、**複数タグ**を持てる。
- **UI**: クリップカード / 動画メタバーにタグチップを表示・追加・削除。タグ入力は既存タグの補完付き。
  クリップビュー / ライブラリの絞り込みにタグ条件（AND / OR）を追加。
- **時間帯の補助**: `videos.recorded_at`（撮影時刻・取得済み）から時間帯を**自動サジェスト**できる（手動上書き可）。
- **永続化**: 新テーブル `tags(id, name, category)` + 中間表 `item_tags(tag_id, target_type, target_id)`
  （`target_type = 'video' | 'segment'`）。または簡易に `labels(target_type, target_id, key, value)`。
- **論点**:
  - まず区間（クリップ）だけにするか、動画にも付けるか。
  - カテゴリ（名前空間）を第一級にするか、`key:value` 記法の運用に留めるか。
  - 将来のモーションタグ（Phase 3 `motion_tags`）との統合（自動タグ + 手動タグを同じ土俵に）。

### Phase 2.9 — クリップ並び順の自動提案（構成アルゴリズム）★構想（2026-07-17）
[../reference/drone-editing-tips.md](../reference/drone-editing-tips.md) の「並べ方の 7 原則」を
スコア関数に落とし、**LLM ではなく決定的なアルゴリズム**でシーケンスの並び順を提案する。
設計の詳細は [../reference/clip-ordering-algorithm.md](../reference/clip-ordering-algorithm.md) を参照。

- **方式**: 遷移コスト付きの並べ替え最適化（章分け → 貪欲 + 2-opt → 冒頭/締めの特別処理）。
  決定的・説明可能・オフラインで、サイドカーなしの最小構成を崩さない。
- **提案は下書き**: 新しいシーケンスとして生成し、ノードグラフ上でユーザーが微調整。
  各接続に理由チップ（「同方向」「高度が下がる」等）を表示。
- **構成リントと表裏一体**: スコア関数を共通実装にし、「既存の並びの違反検出（リント）」と
  「違反が少ない並びの生成（提案）」の両方に使う。
- **依存**: Phase 2.8 の名前空間付きタグ（`motion:` / `dir:` / `scale:` / `speed:` / `alt:`）が
  実質の前提。クリップの評価（星 or `見せ場` タグ）は ⑦（冒頭に最高のカット）に必要で要検討。
- **段階**: v1 スコア + 2-opt（現状タグの `key:value` 運用で開始可）→ v2 `recorded_at` 章分け +
  評価 → v3 GPS 章分け（Phase 3 解析枠）。詳細は設計メモの「段階的実装案」。

## オープンな設計判断（着手前に詰めたい）

1. **HEVC 10bit / D-Log のプレビュー再生**: OS の HEVC 対応に依存するか、取り込み時に低解像度プロキシを生成するか。
   → プロキシ生成をデフォルト ON にするか要判断（実務上の最大の落とし穴）。
2. **キーフレームスナップの丸め**: in=前 / out=後 で確定するか、最寄りキーフレームにするか。
3. **flight_group 推定ロジック**: 連番 + 撮影時刻連続 + 同一解像度/fps のどれを主キーにするか。
4. **サムネイル生成タイミング**: 取り込み時バッチか、表示時遅延生成 + キャッシュか。
5. **ffmpeg バイナリ**: システム依存か同梱か（配布と HEVC 対応の安定性）。
6. **クリップモード（クリップ一覧タブ）の存廃**（2026-07-12 起票）:
   シーケンス画面のクリップエリアが育った結果（クリック再生 = クリップ範囲バー + ループ、
   in/out ナッジ、タグ絞り込み・検索、選択強調）、クリップモードと役割がかなり重複してきた。
   - **現時点でクリップモードにしかないもの**: ①複数選択 → 動画横断のまとめて書き出し、
     ②カード上のラベル編集・タグ付与/削除、③ソート（動画順/新しい順/長い順/ラベル順）と
     元動画絞り込み、④カード単位の書き出し/削除。
   - **統合案**: ①〜③をシーケンス画面のクリップエリアへ吸収し、タブを「ライブラリ /
     シーケンス」の 2 つにする。画面を跨ぐ「編集ジャンプ」系の機能も不要になる。
   - **保留の理由**: シーケンスを介さない素材整理（区間マーク → 個別書き出し = 当初 MVP）の
     使い方ではクリップモードが横断管理のハブ。パレットに管理機能を全部載せると重くなる
     トレードオフもある。
   - **判断基準**: 「クリップモードを開くのは編集ジャンプで飛ばされたときだけ」という使い方が
     続くようなら統合に踏み切る。着手時は移行設計を本ファイルに書いてから。
